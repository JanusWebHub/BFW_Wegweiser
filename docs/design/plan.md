## Plan: Grow a usable router from a demo graph

Build cumulatively on `local/simpler`. Every level ends with a working, clearly labeled browser app and a testable input/output; early levels use a fictional geometry-aligned graph, not an architectural claim. Separate verified SVG authoring and graph compilation as a parallel track; substitute its output only after a contract test and human plan review. Keep analytics and feedback on a later, separate branch. The user executes all state-changing git commands and writing scripts; no repository changes have been made during planning.

### Decisions established
- User chose a user-facing browser result at *every* level, including demo levels.
- User chose to keep analytics requirements off `local/simpler` when adopting selected `feature/sql` content. Cherry-pick selectively or split commits under user control: do not merge whole commits carrying analytics into the active rulebook just to gain input/output requirements.
- `docs/devlog.md` is historical and immutable; `feature/sql` stays independent. The attached Claude overhaul is a reference for intended final pipeline, not an all-at-once execution schedule.
- Treat `src/fixtures/demo-routing-graph.json` as authored test input and `build/routing-graph.json` as the eventual generated real artifact. A demo browser must state clearly that routes and geometry are fictional. Real SVG/compiled output must conform to the same versioned contract; do not fake building coordinates or names.

### Level 1: Small fictitious graph to browser (first real change of behavior)
1. Define a versioned minimal routing-graph contract: zone ids and `crossable`, portal ids each joining two zones plus coordinates, zone-portal index (or derive it deterministically), traversable segments with two portal ids, zone id, nonnegative distance and oriented polyline geometry, optional nonnegative directed state/segment special costs, provenance marker and coordinate frame. Keep core contract separate from browser export. The demo graph and a tiny matching diagram/SVG must use the same coordinates.
2. Author a compact fixture under `src/fixtures/` (e.g. exterior, two non-crossable rooms and two crossable circulation zones with an alternative path). Include a non-crossable zone with two portals so a cheaper illegal shortcut can expose faulty transit handling. Each crossable portal pair used by search has a segment. All nodes/portal references and geometry are consistent. No Python hardcoded building rows.
3. Adapt `shortest_route`, `route_from_states`, `validate_routes`, and `calculate_all_routes` in `src/compute_routes.py`: multi-source/outbound and multi-target/inbound state search; no non-crossable intermediate; same-zone route is one zone; unreachable is a valid per-pair result; correct sum of state, segment and distance costs. Reject invalid graphs and negative transition weights instead of missing segment KeyErrors or silently invalid Dijkstra assumptions. First use direct fixture input; no dependency on SVG parser.
4. Export demo precomputed routes with a small browser-facing JSON/JS asset under `web/data/`, load JS first for file:// with optional HTTP JSON fallback, and make one existing client into a conspicuously DEMO-labeled page that renders the matching demo plan, route and basic instructions. Rename/move/delete conflicting old web files only in the same completed replacement step, by user git commands; never leave an empty index. Existing selects can remain in this level.
5. Completion: open the local demo page from file:// and HTTP; route one ordered pair, a same-zone pair, and an unreachable pair; assertions establish alternate-path winner, non-crossable endpoint transit exclusion and total-cost sum. `python -m unittest discover -s src` checks route and serialization contract. The committed fixture survives independently of any compiler and is not named `build/routing-graph.json`.

### Level 2: Routing decisions and variants, still demo
1. Add routing config with explicitly nonnegative directional special state/segment costs and a named variant disabling transit through an additional zone. Preserve base graph geometry; represent per-variant crossability and precompute ordered zone pairs separately. Confirm unreachable in one variant does not break the rest.
2. Add browser variant selector only when multiple variants exist, and make the display recalculate by lookup, not graph search in JS. Add small tests for directional cost, variant difference, tie behavior, complete pair coverage and unchanged geometry.
3. Completion: same demo app switches variants and shows route/unreachable appropriately, from file:// and HTTP. The real graph compiler is not needed.

### Level 3: Input resolution and client lookup, still demo
1. Add a tiny, explicitly fictional public-location catalog to the demo export: canonical zone ids, verified-for-demo display names, typed room aliases, optional short quick choices. Keep algorithm accepting zone ids only. Distinguish routable zones from publicly searchable locations.
2. Replace full-zone selects with two free-text search fields and bounded suggestions. Normalize harmless case/space differences, resolve one-to-one numbers/names, require explicit choice for multi-zone aliases, show unknown/ambiguous input errors. On submit, `web/script.js` looks up precomputed `routes[variant][start][target]`; it never searches the graph.
3. Completion: room number, name, ambiguity, swap and invalid-input interactions work in the demo browser; keyboard interaction and no full inventory are checked. Test the resolution contract separately from Python routing.

### Level 4: Static route presentation, still demo
1. Adapt `drawRoute`/`orientedGeometry` and `makeInstructions` to portal/zone sequence and segment geometry with no invented access/transit roles. Show start/target, plan orientation, instructions, same-zone and unreachable states. Do not imply a precise location within a zone or that the route is followed; no live progress/rerouting.
2. Add an always-accessible German explanation that no live location is tracked, visible before or when a route first appears. Browser works on desktop/mobile and file:// plus HTTP.
3. Completion: a user can enter a fictional start and target, inspect a correctly oriented route and readable instructions in the demo app, and understand that it is a static demonstration. Search, output and fixtures are independently tested; no SVG compiler or real room catalog required.
