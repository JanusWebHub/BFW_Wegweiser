## Conceptual Map: Wegweiser Lifecycle & Pipeline

### I. THREE LIFECYCLE PHASES

#### 1. Development Lifecycle
**Purpose**: Creating/changing code, authored assets, tests, configuration.

**Artifacts**:
- Source code: [src/build_database.py](src/build_database.py), [src/calculate_routes.py](src/calculate_routes.py)
- Authored SVG: [web/assets/bfw-eg-ost.svg](web/assets/bfw-eg-ost.svg) 
- Tests: [src/test_main.py](src/test_main.py)
- Configuration: Hardcoded data tables (ZONE_ROWS, PORTAL_ROWS, WALL_ROWS in [build_database.py](src/build_database.py#L18-L72))

**Key decision**: [docs/system-design.md](docs/system-design.md#1-modeling-pipeline) explicitly establishes "human-in-the-loop, computer-assisted modeling" separating visual (architectural plans, SVG) and machine-readable (graphs) representations.

---

#### 2. Offline Build/Modeling Pipeline
**Purpose**: Transform authored assets and configuration into precomputed static data for browser consumption.

**Three-stage process** (following [docs/system-design.md § 1](docs/system-design.md#1-modeling-pipeline)):

**Stage A: Structural Data Derivation**
- **Input**: Hardcoded zone/portal/wall configuration ([build_database.py](src/build_database.py#L18-L98))
- **Operations**: [build_database.py](src/build_database.py#L156-L211) derives:
  - `zone_index`: Maps zone → list of portal IDs
  - `segments`: Portal-pair traversals through zones with distance & geometry
  - Three graph types: `adjacency` (rooms/walls, unrouted), `connectivity` (zones/portals), `routing` (portals/segments)
- **Output**: [database.json](database.json) (zones, portals, segments, zone_index, routing graph structure)
- **Validation**: [validate_source](src/build_database.py#L114-L137) checks zone-room mapping, portal distinctness, portal zone existence, zone non-emptiness

**Stage B: Route Precomputation**
- **Input**: [database.json](database.json)
- **Algorithm**: [calculate_routes.py](src/calculate_routes.py#L46-L95) runs multi-source multi-target Dijkstra on directed portal states:
  - State = `(zone_from, portal, zone_to)` (rulebook [§4.2](docs/rulebook.md#42), implementation uses tuple representation)
  - Search from all outbound states of start zone to all inbound states of target zone
  - Cost = segment distance + state special cost ([meta.cost_formula](database_with_routes.json#L10))
  - Excludes `aussen` ("exterior") as intermediate zone unless it is the target
- **Output**: [database_with_routes.json](database_with_routes.json) (same structure + `routes` array containing all 576 precomputed ordered zone pairs)
- **Validation**: [validate_routes](src/calculate_routes.py#L119-L161) checks pair completeness, endpoint correctness, alternation (zone|portal|zone), no exterior intermediate, portal-zone adjacency, cost sum

**Stage C: Browser Export** (implicit)
- **Input**: [database_with_routes.json](database_with_routes.json)
- **Output**: Loaded directly by [east_wing.js](web/east_wing.js#L52) via fetch
- **Note**: No intermediate transformation; database serves as authoritative browser data source

---

#### 3. Runtime Operation (Browser Client)
**Purpose**: User input → static lookup → visualization.

**Flow**:
1. **Load**: [east_wing.js:loadPrototype](web/east_wing.js#L51-L67) fetches [database_with_routes.json](database_with_routes.json) and [web/assets/bfw-eg-ost.svg](web/assets/bfw-eg-ost.svg)
2. **Input Resolution**: User selects start/target zones via `<select>` (currently: [east_wing.html](web/east_wing.html#L43-L51); future: [plan.md Level 3](../memories/session/plan.md#level-3-input-resolution-and-client-lookup-still-demo) proposes free-text search with normalization)
3. **Route Lookup**: [east_wing.js:renderSelectedRoute](web/east_wing.js#L165-L180) performs **constant-time array access**: `database.routes[startZone][targetZone]` — NO search algorithm runs here
4. **Visualization**:
   - [drawRoute](web/east_wing.js#L99-L135): Renders segment polylines with role styling (access/transit)
   - [makeInstructions](web/east_wing.js#L137-L163): Generates German navigation instructions from portal chain and segment roles
5. **Display**: Route summary (distance, portal count, cost) and markup rendered to [east_wing.html](web/east_wing.html#L56-L65) panels

**Critical distinction**: All route computation is **offline**. Runtime has zero algorithmic work.

### II. MODEL VS SYSTEM DESIGN VS IMPLEMENTATION TERMINOLOGY

| **Concept** | **Model (Rulebook)** | **System Design** | **Implementation** |
|---|---|---|---|
| **Graph nodes** | Zone (§1.2), Portal (§1.4) | Zones abstract simplified plan; portals are crossable midpoints | `zones`, `portals` dicts in database.json |
| **Graph edges** | Segment (§1.5: traversal portal→portal through zone) | Routing graph constructed from connectivity graph + movement geometry (§3.3) | `segments`: id, zone_id, portals[2], distance, geometry |
| **Traversal unit** | State (§4.2: zone_from \| portal \| zone_to) with optional cost (§4.2) | "Directed transition" enabling routing variants and multi-source/multi-target search | `State = tuple[str, str, str]` in calculate_routes.py; serialized as `state_chain` in route output |
| **Route** | Alternating zone\|portal\|zone sequence (§4.4) | "Portal chain determines zone sequence" (§4.6) | `sequence` (flattened), `portal_chain`, `zone_sequence` in precomputed route |
| **Crossable vs Non-Crossable** | Zone attribute; non-crossable zones are endpoints only (§1.2) | Marking additional zones non-crossable creates routing variant (§3.3) | Only `aussen` ("exterior") universally non-crossable; others by kind (room, corridor, etc.) or routing variant config |
| **Cost** | Special costs assigned to states and segments (§4.3, §4.2) | "Tuning decision when routing graph constructed" (System Design § 2) | `special_state_costs` dict keyed by `zone\|portal\|zone`; segment cost is distance only |
| **Search** | Multi-source multi-target lowest-cost search on routing graph (§4.5) | Performed once during offline build; routes serialized for browser lookup | Dijkstra in calculate_routes.py; browser does lookup only |
| **Query** | Zone-to-zone request (§4.1: start/target as zones only) | Implemented as state outbound/inbound (§4.5) | Browser selects zones; JavaScript array lookup; no query runtime logic |

### III. CRITICAL TERMINOLOGY AMBIGUITIES & CORRECTIONS

#### A. **"Search" Meaning (Runtime vs Offline)**  
**Issue**: The rulebook (§4.5) describes "search" as a runtime algorithm. The implementation performs it offline.

**Clarification**:
- **Rulebook intent**: "The search produces a portal chain" (§4.6) — describes the algorithmic concept
- **System reality**: [calculate_routes.py](src/calculate_routes.py#L46-L95) runs offline during build phase; **browser has no search logic**
- **Browser operation**: [renderSelectedRoute](web/east_wing.js#L165-L180) is a **constant-time lookup** into precomputed `routes` array, not a search
- **Implication**: Terms "query" and "search" should clarify offline (build-time) vs runtime (presentation) distinction

**Recommendation**: Distinguish "offline route computation" (precomputed, Phase 3 in [implementation-plan.md](docs/implementation-plan.md#phase-3)) from "runtime route resolution" (browser lookup).

---

#### B. **"Segment" Definition Mismatch**  
**Rulebook (§1.5)**: "A segment is a traversal through one zone, from one portal to another."

**Implementation**: [build_database.py](src/build_database.py#L83-L103) constructs segments as portal-pair combinations within a single zone:
```python
for portal_a_id, portal_b_id in combinations(portal_ids, 2):
    geometry = segment_geometry(...)
    segment_id = f"segment:{zone_id}:{portal_a_id}:{portal_b_id}"
```

**Key distinction**: A segment stores:
- `zone_id`: The zone traversed
- `portals`: Two portal IDs (unordered pair)
- `distance`: Computed distance
- `geometry`: Polyline (potentially via movement center for corridors/halls)

**Note**: In route output, `segment_ids` list is indexed by portal position in the route, and [orientedGeometry](web/east_wing.js#L77-L80) reverses geometry if portal order doesn't match segment definition order.

---

#### C. **"State" Serialization & Representation**  
**Rulebook (§4.2)**: "State is written zone_from | portal | zone_to."

**Implementation**:
- **In algorithm**: `State = tuple[str, str, str]` (untyped tuple)
- **In database**: Stored both as flattened `sequence` (e.g., `[zone1, portal1, zone2, portal2, zone3, ...]`) and structured `state_chain` (list of dicts with keys `zone_from`, `portal_id`, `zone_to`)
- **In browser output**: `state_chain` array; `sequence` for human display

**Concern**: No explicit type definition; state construction via tuple indexing is fragile across files.

---

#### D. **"Special Cost" Application Scope**  
**Documented (database.json:meta)**: "segment.distance + destination_state.special_cost"

**Actual implementation** ([calculate_routes.py](src/calculate_routes.py#L69-L71)):
```python
next_cost = current_cost + segment["distance"] + special_costs.get(state_key(next_state), 0.0)
```

**Clarification**: Special costs apply to **states** (zone_from | portal | zone_to), not segments. A state's cost is paid whenever that specific directed transition is made. The cost formula should read: `segment_distance + state_special_costs_for_all_states_in_route`.

**Example** ([build_database.py](src/build_database.py#L70-L72)):
```python
SPECIAL_STATE_COSTS = {
    "flur_west|p07|TR9": 12.0,  # Cost of entering staircase via this portal
    "TR9|p07|flur_west": 12.0,
}
```

These are **directional** — reversing the state reverses the direction, creating different costs.

### IV. INTERFACES & ARTIFACTS

#### Between Development and Offline Build

| **Stage** | **Producer** | **Artifact** | **Consumer** | **Format** |
|---|---|---|---|---|
| Structural data | [build_database.py](src/build_database.py) (hardcoded config) | [database.json](database.json) | [calculate_routes.py](src/calculate_routes.py) | JSON: zones, portals, segments, zone_index, connectivity/routing graphs |
| Route computation | [calculate_routes.py](src/calculate_routes.py) | [database_with_routes.json](database_with_routes.json) | [east_wing.js](web/east_wing.js) | JSON: adds `routes[zone][zone]` with sequence, portal_chain, costs, geometry |
| Visual assets | Hand-authored | [web/assets/bfw-eg-ost.svg](web/assets/bfw-eg-ost.svg) | [east_wing.html](web/east_wing.html) via DOM injection | SVG with semantic id groups (zone-*, portal-*) |

**Contract expectations** ([implementation-plan.md](docs/implementation-plan.md#contract)):
- SVG must have zones and portals as semantic groups with stable IDs
- Database must match SVG id references
- Zone coordinate frame shared between SVG viewBox and segment geometry
- Current implementation: **SVG IDs hardcoded to match build_database.py generated ids**

---

#### Between Offline Build and Runtime

**Serialization format** (database_with_routes.json structure):

```
meta:
  schema_version, model, floor, coordinate_system (viewBox, unit), 
  svg_path, cost_formula, route_count, routing_algorithm
zones: { zone_id → {id, kind, label, svg_id, movement_center} }
portals: { portal_id → {id, zones[2], point[x,y], virtual, svg_id} }
segments: { segment_id → {id, zone_id, portals[2], distance, geometry[[x,y],...]} }
special_state_costs: { "zone|portal|zone" → cost }
indexes:
  zone_portals: { zone_id → [portal_ids] }
graphs:
  adjacency: {nodes: [room_ids], edges: [wall_dicts with portal_id refs]}
  connectivity: {nodes: [zone_ids], edges: [boundary_dicts with portal_id refs]}
  routing: {nodes: [portal_ids], edges: [segment_dicts]}
routes: { zone_id → { zone_id → {status, sequence, portal_chain, zone_sequence, 
                                   state_chain, segment_ids, segment_zones, 
                                   segment_roles, distance, special_cost, total_cost} } }
```

**Note**: `adjacency` and `connectivity` graphs are serialized but not used by browser; routing graph is implicit in segments + zone_index.

### VI. KEY FINDINGS & CORRECTIONS

1. **Process separation is strict**: Build pipeline is offline and deterministic; browser is a presentation-only layer. This is architecturally sound and documented in [README.md](README.md#Architecture).

2. **"Search" terminology requires clarification**: The model describes a runtime algorithm; the system implements it offline. No browser-side graph traversal occurs. Future documentation should distinguish "offline route computation" from "runtime route lookup."

3. **Missing SVG contract enforcement**: The [implementation-plan.md](docs/implementation-plan.md#contract) specifies SVG contract requirements (semantic groups, stable IDs, coordinate frame alignment, portal references, no overlaps), but [build_database.py](src/build_database.py) hardcodes zones/portals rather than parsing them. A validator is planned but not yet implemented. Risk: hand-authored SVG could drift from hardcoded data without detection.

4. **State cost formula is correctly implemented but documentation is imprecise**: Costs apply to directed states (zone_from | portal | zone_to), not segments. The database meta field should clarify: `"sum of segment distances + sum of state special costs for all states in route"`.

5. **Crossability model is underdeveloped**: The rulebook defines a crossable attribute for zones (§1.2), and system design mentions routing variants (§3.3), but implementation only hardcodes `aussen` as non-crossable. Variant support (including zone non-crossability toggling) is planned but not yet implemented.

6. **Zone "kind" is implementation-specific**: The database stores `kind: room | corridor | exterior | service | stairs | hall`, which is neither in the rulebook nor system design — it's an implementation detail used for segment geometry inference ([build_database.py](src/build_database.py#L177-L183)).

7. **Artifact naming opportunity**: Current `database.json` and `database_with_routes.json` are descriptive but generic. Consider `routing-graph.json` and `routing-graph-with-precomputed-routes.json` to clarify their graph-centric purpose and distinguish from future multi-facility or multi-floor consolidations.

8. **State representation is untyped**: Using tuples for states instead of a `State` dataclass risks runtime errors if index ordering is wrong. Consider introducing a type for clarity across [build_database.py](src/build_database.py), [calculate_routes.py](src/calculate_routes.py), and [east_wing.js](web/east_wing.js) (even if representation is still JSON at boundaries).
